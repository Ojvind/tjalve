# Tjalve

Multi-user training-plan tracker. Each user has their own login, plan and
progress; nobody can see anyone else's.

## Stack

- `apps/api` — Fastify + TypeScript, native `mongodb` driver, bcrypt + JWT auth.
- `apps/web` — Next.js (App Router), deployed to Vercel. Talks to the API
  through its own Route Handlers (`/api/auth/*`, `/api/progress/toggle`),
  never directly from the browser.
- MongoDB — self-hosted (own container in `docker-compose*.yml`), not Atlas.

The one rule the whole thing hangs on: the API derives the logged-in user
from the verified JWT (`request.userId` in `plugins/auth.ts`) and scopes
every `plans`/`progress` query by it. Nothing ever accepts a user id from
the client.

## Local dev

```bash
cp .env.example .env            # set SECRET to something real
make dev-up                     # mongo + api on :4100

cp apps/web/.env.local.example apps/web/.env.local
cd apps/web && npm install && npm run dev   # :3000
```

Create a user and load their plan:

```bash
cd apps/api
npm run seed-user -- --email you@example.com --name "You" --password <password>
npm run seed-plan -- --user you@example.com --plan seed/salen-mora.json
```

Two seed plans already exist, generated from the two source files you gave me:

- `apps/api/seed/salen-mora.json` — generated by `npm run build:salen-mora`
  (`scripts/generate-salen-mora.ts` ports the template/week generator that
  used to run in the browser in `salen-mora-plan.html`).
- `apps/api/seed/linus-rehab.json` — generated by `npm run build:linus`
  (`scripts/generate-linus-rehab.ts`, transcribed from
  `rehabprogram_Linus_v6.pdf`; the day-by-day table in that script is the
  thing to check if a number ever looks off).

Re-run either `build:*` script and re-run `seed-plan` any time a plan changes
— it's an upsert keyed on `(userId, slug)`, so it's safe to repeat.

To add a new plan (e.g. the Ironman block after Mora), it doesn't need a new
data model — just a new seeded plan document for the same user, with its own
`slug`, `title` and `goal` and sessions whose `sport` matches what's being
trained that cycle.

## Deploying

- **Web**: `vercel link` in `apps/web`, then set `NEXT_PUBLIC_API_URL` to the
  production API URL in Vercel's env settings. Deploys on push as usual.
- **API + Mongo**: on the Hetzner box, alongside your other apps —
  `cp .env.example .env` (real `SECRET`, `MONGO_USER`, `MONGO_PASSWORD`),
  then `make prod-up`. The prod compose file joins the external
  `yggdrasil_default` network as `tjalve-api`, so add a block to
  `yggdrasil`'s `Caddyfile`:
  ```
  api.tjalve.<domain> { reverse_proxy tjalve-api:4000 }
  ```
  and point `NEXT_PUBLIC_API_URL` at that host.
- **Backups**: not automatic. Add `tjalve` to the `STACKS` array in
  `yggdrasil/scripts/backup-mongo.sh` if you want it covered by the nightly
  `mongodump` cron.
- Seed production users/plans the same way as local, just with
  `DATABASE_URL` pointed at the prod Mongo (e.g. over an SSH tunnel, the way
  your other apps' `push-prod-to-local-db.sh` scripts do it).

## Notes / things I skipped for scope

- No tests yet (vitest 4.x hit a known npm arborist bug on a clean install;
  pull it back in — devDependency only — when you add real tests).
- No admin UI, by design — seeding is a CLI step you run yourself.
- The original Sälen–Mora HTML had an animated SVG course-profile graphic;
  I didn't rebuild that here to keep scope sane. Easy to add later as a
  component on the plan page if you want it back.
